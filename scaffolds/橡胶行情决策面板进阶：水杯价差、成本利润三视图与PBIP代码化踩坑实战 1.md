## 一、 水杯价差：天然橡胶产业链最敏锐的“微观神经”

在天然橡胶的现货贸易与期货交易中，很多投资者往往习惯盯着宏观库存和盘面持仓，但经验丰富的产业研究员最先看的，一定是 **水杯价差**。

```
                    ┌──► 离心加工 ──► 浓缩乳胶 (Latex) ──► 手套 / 避孕套 / 发泡海绵
                    │
新鲜胶乳 ──► 【田间分流】
(Field Latex)       │
                    └──► 胶杯凝固 ──► 杯胶 (Cup Lump) ──► 20号标胶 (STR20) ──► 轮胎制造
```

### 1. 什么是“水”与“杯”？
- **胶水（水）**：割胶后直接收集的新鲜液态天然胶乳（DRC 干胶含量通常在 30%~35% 左右）。它主要供应初加工厂离心加工为 **浓缩乳胶（Latex Concentrate）**，或制作高品级烟胶片（RSS）与全乳胶。
- **杯胶（杯）**：割胶后未直接收集，而是留在胶杯中自然凝固形成的块状凝胶（DRC 约 50%~60%）。它是标胶加工厂生产 **20号标准胶（STR20 / TSR20 / 轮胎胶）** 的直接核心原料。

**水杯价差公式**：
$$\text{水杯价差} = \text{泰国田间胶水价格 (THB/kg)} - \text{泰国杯胶价格 (THB/kg)}$$

### 2. 价格背后的原料争夺与博弈逻辑
水杯价差本质上是 **浓乳/全乳产业链 与 标胶/轮胎产业链 对上游生胶乳资源的争夺战**：

1. **价差走阔（高位溢价）**：
   当医疗手套、乳胶制品等下游需求旺盛，浓缩乳胶加工利润丰厚时，加工厂会大幅抬高田间胶水收购价抢原料。胶农受利益驱动，会全量交付新鲜胶水，导致 **留在树上凝固成杯胶的比例被急剧挤压**。此时杯胶严重短缺，迫使 STR20 标胶加工厂不得不大幅上调杯胶采购价，从而在成本端对 **STR20、NR 20号胶期货以及整个标胶现货价格形成极强的刚性成本支撑**。
2. **价差收窄甚至倒挂（低位低估）**：
   当浓缩乳胶下游需求低迷、加工厂库存积压时，工厂会压低胶水收购价。胶农发现卖胶水不再划算，便倾向于让胶水自然凝固成杯胶出售，导致 **标胶原料供应宽松充裕**，标胶的成本支撑随之弱化。
3. **套利与研判指引**：
   水杯价差是研判 **RU（以上海全乳胶为标的，与胶水/浓乳高度关联）与 NR（以20号标胶为标的，直接以杯胶为原料）跨品种价差**、现货加工毛利边际拐点的最先验核心指标。

为此，我们在报表的 `水杯价差` 页面中，不仅重构了多年季节性走势对比，还在页面底部嵌入了直观的产业逻辑说明卡片，让看盘者在扫过曲线的同时，秒懂当前的原料分流状态。

## 二、 成本利润模型：从静态数据到“单页三视图”交互

过去我们的【成本利润】页面相对简陋，只有一张横向表格，列出各路径的当前原料折算成本与利润，缺乏历史时间序列的纵深观察。如果按照传统做法——“想看明细做一个页面，想看利润做个页面，想看利润率再做一个页面”，整个报表很快又会陷入页面膨胀的恶性循环。

### 1. 业务指标的完整下沉
我们在后台 MySQL 数据库中沉淀了 `view_rubber_processing_cost_profit` 与 `view_rubber_cup_lump_str20_margin_history` 视图，打通了两大核心定价体系：
- **产地 FOB 口径**：
  $$\text{FOB 生产成本 (USD/吨)} = \frac{\text{杯胶价格 (THB/kg)} \times 1000 \times 1.025 (\text{损耗}) + 6000 (\text{加工费 THB})}{\text{USD/THB 汇率}}$$
  $$\text{FOB 单位加工利润} = \text{STR20 FOB 价格 (USD/吨)} - \text{FOB 完全生产成本}$$
  $$\text{FOB 利润率} = \frac{\text{FOB 单位加工利润}}{\text{FOB 完全生产成本}} \times 100\%$$
- **国内完税口径**：
  纳入了海运费（30 USD/吨）、人民币汇率（USD/CNY）、海关固定税（1500 元/吨）以及 13% 增值税，精准还原国内进口到港完税后的实际利润与利润率。

### 2. 单页三视图融合交互架构
在【成本利润】页面上，我们通过 **3 个视觉对象（同位置重叠） + 3 个操作按钮 + 3 个书签（Bookmarks）**，实现了极简的“单页三视图”交互体验：

```
+-------------------------------------------------------------------------+
|                                                                         |
|   [ 视 图 区 域 (x:10, y:0, w:1260, h:620) ]                             |
|   · 视图 A：成本利润综合多路径明细表 (tableEx)                           |
|   · 视图 B：加工利润历史走势柱状图 (FOB vs 国内完税) (clusteredColumnChart)|
|   · 视图 C：利润率历史走势柱状图 (FOB% vs 完税%) (clusteredColumnChart)   |
|                                                                         |
+-------------------------------------------------------------------------+
| [ 按 钮 1: 成本利润明细 ] | [ 按 钮 2: 加工利润 ] | [ 按 钮 3: 利润率 ]    | (y:630)
+-------------------------------------------------------------------------+
|                        全 局 底 部 导 航 栏                              | (y:675)
+-------------------------------------------------------------------------+
```

- **按钮 1【成本利润明细】** $\rightarrow$ 触发书签 `b7p114ef35531a2692e1`，全屏展示涵盖胶水转浓乳、杯胶转标胶、丁二烯转顺丁等各加工路径的完全成本、售价与利润明细；
- **按钮 2【加工利润】** $\rightarrow$ 触发书签 `b7p286b0e920633366e2`，瞬间切换为历史加工利润柱状图，清晰查看产地 FOB（美元）与国内完税（人民币）加工利润的历史波动中枢；
- **按钮 3【利润率】** $\rightarrow$ 触发书签 `b7p314ef35531a2692e3`，瞬间切换为利润率周期柱状图，直观判断当前加工厂处于暴利期、微利期还是深度亏损期。

页面数量为零增长，信息承载力与分析效率提升了 300%。

## 三、 PBIP 代码化开发避坑实战指南

在脱离 Power BI Desktop 界面、完全通过代码（TMDL 语义模型 + PBIR JSON 报告定义）以及 AI Agent 进行自动化编程时，我们遇到了几次经典的底层报错。这些错误极具共性，值得所有从事 PBIP 代码化工程的同学深入沉淀：

### 避坑 1：Analysis Services 全局度量值重名冲突
- **错误现象**：Power BI 启动加载项目时报错 `PFE_TM_OBJECT_NAME_ALREADY_EXISTS` —— *“无法添加名为‘产地FOB_单位加工利润_USD_吨’的‘Measure’，因为‘Model’模型中已有同名的‘Measure’。”*
- **根因剖析**：在传统关系型数据库（如 MySQL/PostgreSQL）中，不同表内有相同列名是完全合法的；但在 Power BI（Tabular Object Model）中，**DAX 允许使用不带表名前缀的无修饰引用 `[MeasureName]`，因此整个模型（Model）范围内的所有度量值名称必须全局唯一！** 如果你在 `A表.tmdl` 和 `计算仓.tmdl` 中定义了同名度量值，即便所属表不同，模型引擎也会在反序列化时彻底抛崩。
- **治理规范**：全局扫描确保每个度量值全局命名唯一，避免在多表重复注册。

### 避坑 2：同表内“度量值与列名”同名冲突
- **错误现象**：报错 `PFE_XL_MEASURE_COLUMN_ALREADY_EXIST` —— *“无法创建‘产地FOB_单位加工利润_USD_吨’度量值，因为已存在同名的列。”*
- **根因剖析**：如果物理数据表 `rubber view_rubber_cup_lump_str20_margin_history` 中已经有一列名为 `产地FOB_单位加工利润_USD_吨`，如果你又在该表内定义同名的度量值 `measure 产地FOB_单位加工利润_USD_吨 = SUM(...)`，Analysis Services 会因对象命名空间冲突直接拒绝加载。
- **最佳实践**：**建立专用的集中式度量值表（如 `计算仓.tmdl`）**。计算仓内只有一张虚拟空列，所有复杂业务度量值统一集中在此，彻底绝缘了“列与度量值同名”的冲突隐患。

### 避坑 3：Fabric PBIR JSON Schema 的严格层次陷阱
在编写书签 `.bookmark.json` 和按钮 `visual.json` 时，语法极其严格：
1. **书签节点的 `objects` 嵌套**：
   在 Bookmark 2.1.0 规范中，`objects` 属性必须包含在 `explorationState` 节点内部（与 `sections` 同级）。如果括号闭合错误导致 `objects` 漏到 root 根节点，Power BI 反序列化时就会报 *“root 属性中包含一个额外的属性 objects”*。
2. **按钮动作 `visualLink` 的属性封装**：
   在 VisualContainer 2.11.0 规范中，`actionButton` 的动作跳转类型和书签 ID 必须完整封装在 `properties` 字典内：
   ```json
   "visualContainerObjects": {
     "visualLink": [
       {
         "properties": {
           "show": { "expr": { "Literal": { "Value": "true" } } },
           "type": { "expr": { "Literal": { "Value": "'Bookmark'" } } },
           "bookmark": { "expr": { "Literal": { "Value": "'b7p114ef35531a2692e1'" } } }
         }
       }
     ]
   }
   ```
   如果把 `type` 和 `bookmark` 写在 `properties` 外侧（与 `properties` 同级），就会触发 *“属性中包含额外的属性 type/bookmark”* 错误。

### 避坑 4：UTF-8 No-BOM 与坐标防重叠铁律
- **严格 UTF-8 无 BOM 编码**：Power BI 对 TMDL 和 JSON 文件的 BOM 头（`0xEF, 0xBB, 0xBF`）是零容忍的，只要多出这 3 个字节就会直接报错。所有自动化生成脚本必须采用标准无 BOM 编码写入。
- **严格坐标避让**：本报表采用底部全局导航栏（`y: 675, h: 38`），所有主图表与按钮的高度必须控制在 `y + height <= 675`，严禁任何负坐标或越界重叠。
